あなたはUX TIMES用語集の「編集差分から執筆ルールを学ぶ週次ジョブ」を実行するエージェント。作業ディレクトリは /Users/takahashi_yuya/workspace/article-creator。

公開された記事は、AIの初稿に人が手を入れたものである。その差分には「いまの執筆ルールで防げていない弱点」が現れる。差分を読んで弱点を言葉にし、執筆ルールの改訂材料として積むのがこのジョブの仕事。**プロンプトそのものは書き換えない。** 反映するかどうかは人が決める。

## Step 1: 差分を集める

```bash
python3 scripts/collect_edit_gaps.py
```

未確認の公開済み記事について `logs/gaps/{今日}/{用語}.md` に差分が出る。「差分を取る対象は無し」なら Step 4 へ飛ぶ。

## Step 2: 差分を読んで分類する

`logs/gaps/{今日}/` の各ファイルを読み、「手が入った箇所」を1つずつ次の観点で分類する。段落番号ではなく**何が起きたか**を書く。

- **事実の誤り**: 人物・年号・数値・出典が直された
- **冗長**: 言い回しが短くされた、重複が削られた
- **段落構成**: 段落が割られた・順序が変えられた・見出しが増減した
- **語彙**: 専門語が言い換えられた、カタカナ語が和語になった
- **具体性**: 抽象的な記述に例や数値が足された
- **調子**: 断定/推量、評価語、体言止めなどが直された
- **追記**: 初稿に無い情報（参考リンク・補足・画像）が足された
- **削除**: まるごと落とされた

分類したら、**執筆原則 P1〜P7（`prompts/02_polishing.md`）と形式ルール F1〜F6（`CLAUDE.md`）のどれに当たるかを必ず決める**。ここがこのジョブの肝で、記事ごとの直しをそのままルールにしてしまう過学習を防ぐ線引きになる。

- **(A) 原則はあるが守られていない**: どの原則の違反かを書く（例: `P3 どの文も新しい情報を1つ運ぶ`）。→ その原則の「確かめ方」が弱い
- **(B) どの原則にも当たらない**: 7つの原則のどれにも当てはめられないときだけ (B) と書く。→ 新しい原則の候補。ただし、まず既存の原則の言い換えで説明できないかを2回考える

事実の誤り（人物・年号・数値・出典）は P1、例や定義が隣の用語のものだった直しは P2 に当てる。この2つは文章の好みではなく関門（出典台帳・成立条件メモ）の漏れなので、どの記事のどの文が台帳を通り抜けたかを書く。

**数える価値のない差分は落とす。** 表記ゆれの吸収漏れ、URLだけの追記、画像の差し込みなど、執筆の指示を変えても防げないものは記録しない。

## Step 3: 観測ログに積む

`prompts/learned/observations.md` の末尾に、今日の日付の節を足す（無ければファイルごと作る）。記事ごとに次の形で書く。

```markdown
## 2026-08-24

### 黄金比（G-008 / v0） — 未反映
- **(A) 段落構成 / P3**: 定義・具体例・補足を1段落に詰めていたのを、人が4段落に割った。「1段落1論点・2〜4文」の確かめ方が初稿で働いていない
- **(A) 冗長 / P3**: 「ひとつの長さを長い部分と短い部分に分けたとき」が「ひとつの長さを2つに分けたとき」に短縮された。後で定義する語を先に出す形で、P3 の確かめ方に「後で定義する語を先出ししていないか」を足す候補
```

- 見出しの `— 未反映` は改訂に取り込むまで残す。人が反映したら `— 反映済み(v2)` に書き換える
- 1記事あたり多くて5項目。細かすぎるものは落とす

## Step 4: たまっていたら改訂案を書く

`prompts/learned/observations.md` の `— 未反映` の記事数を数える。**3本以上なら**改訂案を書く。3本未満なら書かずに終える（サンプルが少ないうちに一般化すると、プロンプトを振り回すことになる）。

改訂案は `prompts/learned/proposal-{今日}.md` に次の構成で書く。

```markdown
# 執筆ルール改訂案（2026-08-24）

対象: 未反映の観測 N本ぶん（用語A・用語B・用語C）

## 1. {何を直すか}

- **根拠**: どの記事で何回observedされたか。実際の書き換え例を1つ引く
- **対象の原則**: P1〜P7 / F1〜F6 のどれか（新しい原則の提案なら、既存の7つで説明できない理由を書く）
- **いまの記述**: `prompts/02_polishing.md` の該当原則の「確かめ方」を逐語で引く
- **改訂案**: 原則の本文は変えず、「確かめ方」の1行を足すか書き換える形で、逐語で書く。記事ごとの具体例（用語名・実際の文）は `observations.md` に残し、原則には書かない
- **効かせ方**: なぜこの書き方なら防げるのか。1〜2文

## 反映のしかた

1. 上の改訂案を prompts/ に反映する
2. `python3 scripts/recipe_version.py bump --note "{改訂の要約}"`
3. observations.md の該当記事を `— 反映済み(vN)` に書き換える
4. 旧版の記事は用語くんが作り直し候補として数える（`@用語くん 古い記事教えて`）
```

- 2回以上observedされたものを優先する。1回きりの直しは、その記事固有の事情かもしれない
- 提案は多くて3件。全部盛りにしない
- **原則を増やす提案は、1回の改訂で最大1件まで**。原則の数が増えるほど、1つ1つの効きが薄れる
- **文体・語彙の好みに踏み込む提案は「案」で止め、断定しない**。最終的な言い回しの判断は人がする

## Step 5: 報告

標準出力に、処理した記事数・分類の内訳・未反映の記事数・改訂案を書いたかどうかを簡潔に出す。**Slackには投稿しない。**
