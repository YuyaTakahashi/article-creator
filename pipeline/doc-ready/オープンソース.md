## 最小限の説明

ソフトの中身を誰でも読み、直し、配り直せるようにする仕組み

オープンソース（Open Source）とは、使う側が自分の手で中身を確かめて直せるようにするために、ソフトウェアの元になるプログラムを誰にでも公開する仕組みである。

ふつうに買うソフトは、動く形だけが手元に届く。中でどう処理しているかは見えない。オープンソースは、元のプログラムをそのまま公開する。誰でも読んで確かめられるし、自分で直したものを配り直してもよい。

たとえば、いま読んでいるこのページを届けているサーバーの多くは、Linuxというオープンソースの基本ソフトで動いている。中身を誰でも読めるので、世界中の技術者が不具合を見つけては直しを送り、送った直しが本体へ入っていく。

つまり、売り手だけが中身を触れるのがふつうのソフト、使う側も触れるのがオープンソースである。

## 読めて、直せて、配り直せる

オープンソースかどうかは、値段ではなく、使う人に何を許しているかで決まる。

許しているのは4つある。誰が何の目的で使ってもよいこと、中身を読めること、直してよいこと、直したものを配ってよいことである。特定の国や業種を使えない相手として外すと、この呼び名は使えなくなる。

許す条件を書いた文書をライセンスと呼ぶ。中身は大きく2種類に分かれる。直したものを配るときは同じ条件で中身も公開するよう求めるものと、元の作者名を残すだけでよいものである。この違いが、自社の製品に組み込めるかどうかを分ける。

無料で手に入ることは多い。ただし、無料であること自体は条件に入っていない。値段だけで判断すると、使ってよい範囲を読み違える。

## 語源・提唱者

1998年まで、この種のソフトを free software と呼ぶのがふつうだった。英語の free には「無料」と「自由」の両方の意味がある。初めて聞いた人はまず値段の話だと受け取るので、説明する側は毎回「ビールのfreeではなく、言論のfreeだ」と言い添える必要があった。企業の側も、無料を掲げる運動に見えて手を出しにくかった。

新しい呼び名の狙いは、初めて聞いた人が値段の話だと取り違えない言葉を用意することにあった。

1998年1月、Netscape が自社のブラウザの中身を公開すると発表した。この動きに合わせて呼び名を変える好機だと考えた Christine¥クリスティーン¥ Peterson¥ピーターソン¥ が、open source software という言い方を思いつく。[本人の回想](https://opensource.com/article/18/2/coining-term-open-source-software)によると、2月5日の会合では自分から売り込まず、参加者のひとりが別の話題の文中にこの語をさりげなく混ぜた。すると、その場の全員がそのまま使い始めたという。

同じ月の末には、Eric¥エリック¥ Raymond¥レイモンド¥ と Bruce¥ブルース¥ Perens¥ペレンズ¥ が [Open Source Initiative](https://opensource.org/about/history-of-the-open-source-initiative) を立ち上げ、どこまでを「オープンソース」と呼んでよいかの条件を文書にした。この文書は、Perens が前年にDebianという配布元のために書いた指針を下敷きにしている。広まったのは、この言葉が思想ではなく、使う側に許される行為だけを指していたからである。企業は運動に加わらなくても、条件さえ守れば自社の製品に取り込めるようになった。

## 一社の都合に縛られない

オープンソースが効いてくるのは、選んだ部品をこの先も使い続けられるかを考える場面である。

中身の見えないソフトを組み込むと、そこから先は売り手の判断に預けることになる。おかしな挙動を見つけても、報告して直るのを待つしかない。値上げがあっても、提供が終わっても、こちらから打つ手はない。別の製品へ移るには作り直しが要る。

元のプログラムが手元にあれば、待たずに自分で直せる。作っていた会社が撤退しても、その時点の中身から枝分かれさせて使い続けられる。

効き先は3つに分かれる。

- **作り手のチーム**：動きが分からないときに中身をそのまま読める。問い合わせて返事を待つ時間が消える。
- **事業**：一社への依存を避けられるので、値上げや提供終了が事業計画を揺らさない。
- **エンドユーザー**：同じ形式を扱う道具が増え、別の製品へデータを移しやすくなる。

ただし、無料で手に入ることと、費用がかからないことは別である。不具合の対応も、危険な欠陥が見つかったときの入れ替えも、使う側の仕事になる。しかも、手入れをしている人数は見た目ほど多くない。[Linux Foundation と Harvard の共同調査](https://www.linuxfoundation.org/research/census-ii-of-free-and-open-source-software-application-libraries)によると、広く使われている部品ほど、記述の大半をごく少数の人が書いている。2024年には、多くのLinuxに入っている圧縮の部品へ、何年もかけて信頼を得た人物が不正な仕掛けを混ぜ込む事件も起きている。

## 使う前にライセンスを読む

使いどころは、どの部品を採用するかを決める技術選定の段階である。

決める前に、使う部品とそのライセンスを1行ずつ並べた一覧を作る。何を使っているか分からない状態が、あとでいちばん効いてくる。この一覧は、危険な欠陥が見つかったときに、自社のどこに影響するかを調べる資料にもなる。

エンジニアだけで決めない。ライセンスは契約の条件そのものなので、法務と一緒に読む。直したものを同じ条件で公開するよう求める種類の部品を製品の中心に据えると、売り方にまで条件が及ぶ。ここを後から気づくと、作り直すしかなくなる。

採用でよく外すのは、無料であることだけを見て選び、手入れの止まった部品を抱えてしまうときである。最後に更新した日はいつか、直しを取り込んでいる人は何人いるかを、決める前に見ておきたい。

同じ考え方はデザインの道具にも広がっている。アイコン集や書体、画面部品の一式がオープンソースで出ているので、自分たちの決まりに合わせて作り替えたうえで使える。
