SQLインジェクション（SQL Injection）とは、入力欄などに命令の一部となる文字列を送り、情報を保存するデータベースへの命令を書き換えて、不正に利用する攻撃である。

たとえば、ログイン画面で入力した利用者名とパスワードを、そのまま命令文につなぐ作りを考える。この作りでは、利用者名に特定の記号を含めることで、パスワードを知らなくてもログインできる場合がある。

## 利用者名の入力で命令が変わる

データベースと情報をやり取りするウェブアプリケーションの多くは、利用者の入力を基に、データベースへの命令文を組み立てている。この命令文を「SQL文」と呼ぶ。組み立て方に問題があり、入力を命令の一部として扱う弱点が「SQLインジェクションの脆弱性」である。

ログイン画面の例では、利用者名に `wiener`、パスワードに `bluecheese` を入力すると、アプリケーションは次の命令文で照合する。これは、利用者名とパスワードの両方が一致する利用者を探す処理である。

```sql
SELECT * FROM users
WHERE username = 'wiener' AND password = 'bluecheese'
```

ところが、利用者名に `administrator'--` を入力し、パスワードを空欄にすると、アプリケーションが組み立てる命令文は次のようになる。

```sql
SELECT * FROM users
WHERE username = 'administrator'--' AND password = ''
```

この例では、入力に含まれる記号によってパスワードの条件が効かなくなる。その結果、攻撃者はパスワードなしで、その利用者としてログインできる。

## 情報の漏えいや改ざんに及ぶ

先ほどのログイン例では、攻撃者が本人確認をすり抜け、不正にログインする。SQLインジェクションによる被害には、このほかに、非公開情報や個人情報の読み取り、情報の書き換えや消去がある。データベースを停止するなどの操作につながる場合もある。

2009年、米司法省は、カード決済処理会社などにSQLインジェクション攻撃で侵入し、1億3,000万件超のクレジット・デビットカードのデータを盗んだとして男を起訴した。この事件で使われた入力内容や命令文の詳細は、参照した出典には示されていない。

## 設計時に入力の渡し方を確かめる

検索窓を新しく作る際の設計確認を、対策の作例として考える。入力された検索語を命令文へ直接つなぐのではなく、命令の骨組みと検索語の値を分けて渡す設計にする。このように、命令と値を分けて渡す方法を「パラメータ化した問い合わせ」と呼び、SQLインジェクションのほとんどを防げる。

命令の骨組みを先に用意し、値を後から結びつける方法を「プリペアドステートメント」と呼ぶ。この方法では、アプリケーションが渡した値に命令として読める記号が含まれていても、データベースはその値を命令ではなくデータとして扱う。先ほどのログイン画面でも、入力によってパスワードの条件を書き換えることを防げる。

ただし、入力値を命令文につないだ後で準備しても、この対策にはならない。設計を確認するときは、命令と値を分けて渡しているかを確かめる。

併せて、アプリケーションがデータベースを利用するためのアカウントには、必要な操作だけを許可する。また、データベース関連のエラーメッセージを利用者の画面に表示しないようにする。

命令と値を分けて渡す対策で防げるのは、入力による命令の書き換えまでである。その利用者が特定の口座の情報を見てよいか、といったアクセスの可否は別に判断する必要がある。
