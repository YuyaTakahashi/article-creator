# article-review スキル

`drafts/{ファイル名}.md` を頭から通して読み直し、(A) 事実関係・情報の正確性・公開リスクの評価と修正、(B) 文章の通し推敲を、この順で行う。
最後にフロントマターへ実施印 `reviewed_at` を書き込み、`article-post` が投稿前ゲートで実施を確認できるようにする。

## このスキルの位置づけ

- article-creator が初稿を自動生成し（内部で article-critic が品質ゲート）、人間が drafts/ を編集したあと、`article-post` で WordPress へ反映する前に実行する。
- WordPress への反映は不可逆なので、その手前で「人間が触った最終形」を事実・リスク・文章の3面から最終確認する。

## article-critic との役割分担

- **article-critic** は採点専用。pass / regenerate / escalate を返すだけで本文を直さない。ファクトチェックも対象外。creator 内部で自動的に回り、yuyaには見せない。
- **article-review（本スキル）** は実際に直す。critic がやらない3点 ―― Webソースでの事実検証・本文編集・投稿前の人間ゲート ―― を埋める。文章の採点だけは critic を呼んで再利用し、ルーブリックの二重実装を避ける。

| | article-critic | article-review |
|---|---|---|
| 役割 | 採点（pass/regenerate/escalate） | 事実検証＋リスク評価＋本文を直す |
| 本文編集 | しない | する |
| 事実検証 | 対象外 | Phase A で実施 |
| 実行タイミング | creator 内部（初稿） | 人間編集後・post 直前 |
| 文章採点 | 4軸ルーブリックを持つ | critic を呼んで再利用 |

## WordPress には触らない（厳守）

このスキルは WordPress への POST・更新・GET・メディアアップロードを一切しない。投稿は `article-post` の責任。
事実検証のための WebFetch / WebSearch（Wikipedia・学術ソース等への参照）は WordPress へのアクセスではないので可。

## 実行手順

引数でファイル名が渡されていればそれを使う。無ければ `drafts/` の一覧を提示して選ばせる。

### Step 0: 読み込み

`drafts/{ファイル名}` を Read で読み込む。存在しなければ `drafts/` の一覧を提示して再選択させる。
research/ に対応するリサーチMD（`research_{topic}_*.md`）があれば、ソース一覧を控えておく（Phase A で使う）。

事実を先に正してから文章を整える。順序を逆にすると、推敲した文をあとで事実修正して壊し、二度手間になるため。

### Phase A: 事実・情報リスク評価

本文の検証対象を洗い出し、信頼できるソースに当てて確かめる。明確な誤りはこの段で先に直す。
research/ にソースがあればまず WebFetch で当たり、足りなければ WebSearch で補う。

- **事実確認**: 人名の表記・スペル、提唱者・提唱年・所属機関、数値・統計、因果関係・歴史的事実。
- **根拠（Greggのジャッジメント軸）**: 断定に「なぜそう言えるか」が裏づくか。裏づかない断定は出典で補強するか「〜とされる」等に和らげる。
- **公開リスク**: 誤情報・古い情報、誤解を招く表現、特定の個人・企業を不当に断定する記述、出典のない引用、権利・引用元表記の欠落がないか。
- **判定**: 各検証対象に「確認済み / 要修正 / 要人間判断」のいずれかを付ける。明確な誤りは自動修正し、判断が割れるものは要人間判断として残す。

修正は MD を直接編集する。修正した事実と根拠（参照URL）を控え、完了報告に残す。

### Phase B: 通し推敲（採点は article-critic を再利用）

Phase A で事実を直したあとの本文を、全体を1回通して整える。
文章の採点ルーブリックは自前で持たず、article-critic を呼んで評価を再利用する。

**0. 構成の無条件矯正（critic を呼ぶ前に必ず実施。critic のスコアに関係なく article-review が本文を直す）**
   - **リードの順序を矯正する**：本文は「① 用語の定義＋（体系・分類・対概念の用語なら）全体像（何のうちのどれか） → ②『たとえば、…』の具体例」の順で始める。**具体例・問いかけ・シーン描写から始まっていたら、定義・全体像の段落を前に出して並べ替える。**「例が先・定義が後」は不可。ここは判断を保留せず、その場でMDを書き換える。
   - **平易さを矯正する**：「データ層／データ活用／マスタ／原本／正規化／レイヤー／エンティティ」等のIT前提語が言い換えなしで残っていないか洗い、初出でかみ砕く（例：原本→「おおもとの記録」）。判定は「その分野を初めて知る人がつっかえず読めるか」。
   - **背景・効果・実務の3点が埋まっているか確かめる**：読者が用語解説を読む主目的にあたる3点なので、欠けていたら埋める。記事内に材料があって書き方が悪いだけならその場で書き換える。材料自体が無い場合は research/ のソースに当たり、ソースにも無ければ推測で埋めず「要人間判断」として残す（基準の詳細は CLAUDE.md 記事の書き方ルール9・10・11）。
     - **語源・提唱者が年表になっていないか**：提唱年と人名だけが並び、当時何に困っていたのか・何を狙って作られたのかが書かれていない記事は不可。「①当時の課題（誰が・どんな現場で・何に行き詰まっていたのか）→ ②何を狙って作られたのか → ③結果何が変わったのか」の順に組み替える。当時の具体的エピソード（実際のプロジェクト・製品・失敗事例）がソースにあれば書き足す。「複雑さが増していた」のような一般論で①が済まされていたら要修正。
     - **効果が抽象語の羅列で終わっていないか**：「一貫性が高まる」「効率化できる」「わかりやすくなる」といった語が、実務で何を意味するのか説明されずに並んでいたら直す。「使わない場合に実務で何が起きるか」→「使うとどう変わるか」の前後対比に書き換え、誰に効くのか（エンドユーザー／作り手のチーム／事業）を補う。リストの各項目が単語だけで終わっていたら補足の文を足す。
     - **後半に実務での使い方があるか**：工程（企画・調査・設計・検証・運用のどれか）／誰と使うか／何がアウトプットとして残るか／ありがちなつまずきと回避策、の4点を確認する。前セクションで述べた効能を言い換えただけの記述になっていたら具体に書き換える。ただし活用法の該当がないトピック（純粋な現象・バイアスの名称など）は、このセクションが無くてよい。

1. Phase A 修正後の全文を `article-critic` に渡し、テンプレ準拠・文章スタイル・読み手目線・読みやすさの4軸で採点する。

   ```
   article_type: ux_glossary
   topic: {記事のtopic}
   difficulty: {フロントマター由来 or 既定0.3}
   it: {フロントマター由来 or 既定0.3}
   proposed_article: <Phase A 修正後の全文>
   attempt_count: 1
   caller: article-review
   ```

2. 返ってきた `regenerate_points` を読み、該当箇所を MD で直接直す。critic は採点だけで本文を直さないので、修正は article-review が行う。
3. 加えて、critic の軸ではカバーしきれない次の観点を人間目線でジャッジして整える。
   - 用語の難易度・専門性に対し、補足が過不足ないか（足す/削るを判断する）。
   - 事実修正で挿入した文が、前後の文と自然につながっているか。
   - 段落間の論理が切れていないか。冒頭・中盤・末尾で同じ話題が重複していないか。
4. 必要なら critic を再度呼んで通過を確認する（往復は最大2回まで）。2回でも通過しない軸があれば、その軸を「要人間判断」として完了報告に残す。

### Phase C: 仕上げと実施印

1. 大きく構成を変える必要が出たら、その旨をyuyaに1行で伝えてから整える。
2. 修正が終わったら、フロントマターに実施印を書き込む。

   ```yaml
   reviewed_at: {YYYY-MM-DD}
   ```

3. 保存したMDをもう一度Readで読み返し、フロントマターに `reviewed_at` が入ったことを確認する。

## 完了報告

```
レビュー対象 : drafts/{ファイル名}.md
reviewed_at  : {YYYY-MM-DD}（記入済み）

事実・リスク評価:
  確認済み      : {件数 or 主な確認点}
  修正した点    : {修正内容と参照URL（あれば）}
  要人間判断    : {判断が割れた点。無ければ「なし」}

内容の充実度（背景・効果・実務）:
  背景・目的    : {補った点 or 「記載あり」 or 「要人間判断（ソースに裏づけなし）」}
  効果          : {補った点 or 「記載あり」}
  実務での使い方 : {補った点 or 「記載あり」 or 「該当なしのため省略」}

推敲の変更点（1〜2行）:
  - {主な推敲修正}

次のステップ: /article-post {ファイル名}.md で WordPress に投稿してください。
```

要人間判断が1件でも残る場合は、報告の冒頭に「⚠ 投稿前にyuyaの確認が必要」と明示し、投稿を急がないよう促す。
