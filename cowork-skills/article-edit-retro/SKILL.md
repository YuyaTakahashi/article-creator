# article-edit-retro（公開後の修正ふりかえり）

yuyaが「◯◯を公開した」と伝えたら、その記事の初稿と公開版を突き合わせ、さらに同じセッションでのやりとりも読み返して、直した理由と「何がいけなかったか」の仮説、修正レベル1〜3の仮説を出す。yuyaが仮説を是正し、確定した内容だけを記事のGoogleドキュメントと観測ログに書き込む。

## なぜこの形にするか

- 修正レベルを差分の量で決めない。リライトで文がまるごと入れ替わっても、意味がほぼ同じなら修正は軽い。1語が分からないだけで記事が伝わらない場合は、差分が小さくても修正は重い（2026-10-05 の打ち合わせでの合意）。レベルは「何を、なぜ直したか」から決める。
- 点数そのものに価値はない。目的は、どの用語にどれだけ手が入ったかを一目で見えるようにし、直した理由の共通点をプロンプト改善につなげることにある。
- 差分だけでは「なぜ」が半分しか分からない。yuyaがチャットで「ここが分からない」と指摘した箇所、試して捨てた案（たとえの作り直しなど）、改稿の途中で事実の意味がずれてレビューで戻した箇所は、初稿と公開版の差分には残らない。プロンプト改善に一番効くのはこの部分なので、セッションのやりとりも必ず材料にする（2026-10-11 エージェンティックRAGでの合意）。
- 週次の学習バッチ（`scripts/weekly-learn-batch.sh` → `pipeline/learn-from-edits-prompt.md`）は、AIだけで差分を分類している。このスキルは同じ仕組みに乗り、yuyaが確認した理由を観測ログに積む。別系統の記録を作らない。

## 実行環境

- WordPressへのアクセスはローカル（Mac）でだけ行う。Coworkからは Desktop Commander の start_process でローカルのコマンドを実行する。サンドボックスからWPへアクセスしない。
- 作業ディレクトリ: `/Users/takahashi_yuya/workspace/article-creator`
- 用語DB: `UX TIMES 用語DB`（fileId `1GEhserUiXQIHG8xNl2jUdLvrD2fHzeWXGkdJ_sZGCgY`）。H列がステータス、J列がWP URL、Q列が `wp_post_id`、W列がGAP確認日。

## Step 1: 対象を特定する

1. yuyaが伝えた用語名で用語DBを読み、`用語` 列の完全一致で行を特定する。ID（G-xxx）・`記事Doc`・`WP URL`・`category_id`・生成バージョンを控える。一致しない、または複数一致したときは、候補を出してyuyaに選んでもらう。
2. `prompts/learned/observations.md` に同じ用語の節があるかを確認する。週次バッチがすでに自動分類していれば、その内容を仮説づくりの材料として読む。
3. 記事Docのタイトルと末尾を読み、共同編集者がすでに修正レベルやふりかえりを付けていないかを確認する。付いていれば、Step 3でyuyaに並べて見せる。
4. 記事Docのタブが1枚かを確認する。複数ある場合は、どのタブが公開版かをyuyaに確かめる（用語くんは先頭のタブしか読まない）。

## Step 1.5: 用語DBを公開済みに揃える

WPで公開ボタンを押しても、用語DBは書き換わらない。ステータスが「下書き作成済み」「レビュー待ち」のままだと、Step 2-1 の差分収集（公開済みだけが対象）から漏れ、WP URL列にも編集画面のリンクが残る。差分を取る前に、次の2つをローカルで行う。これは公開した事実の反映なので、yuyaの確定（Step 4）を待たずに行ってよい。

1. ステータスを公開済みにする。

   ```bash
   cd ~/workspace/article-creator
   python3 scripts/sync_published_status.py
   ```

   WP上で publish になっている行のH列（ステータス）を「公開済み」にする。「作り直し済み」「見送り」の行は触らない。対象の行が出力に出てこず、H列も公開済みでなければ、WP上でまだ公開されていない。Step 2-1 の「差分を取る対象は無し」と同じ扱いで進め、Step 3 の冒頭で1行伝える。

2. J列（WP URL）を公開ページのURLにする。Step 1 で控えた行のQ列（`wp_post_id`）を使い、`?p=` のリダイレクト先から公開URLを取る。

   ```bash
   curl -sIL "https://uxdaystokyo.com/articles/?p={wp_post_id}" | awk 'tolower($1)=="location:"{print $2}' | tail -1 | tr -d '\r'
   ```

   取れたURL（例 `https://uxdaystokyo.com/articles/glossary/{slug}/`）を、その行のJ列に書く。

   ```bash
   gws sheets spreadsheets values update \
     --params '{"spreadsheetId":"1GEhserUiXQIHG8xNl2jUdLvrD2fHzeWXGkdJ_sZGCgY","range":"'"'"'UX TIMES 用語DB'"'"'!J{行番号}","valueInputOption":"RAW"}' \
     --json '{"values":[["{公開URL}"]]}'
   ```

   URLが取れない（`?p=` がリダイレクトしない）ときは、J列を書き換えずに進め、Step 3 の冒頭で1行伝える。

書いたあと用語DBのその行を読み直し、H列が「公開済み」、J列が公開ページのURLになっていることを確かめる。

## Step 2: 材料を集める

### 2-1. 差分

ローカルで次を実行する。`--recheck` は、週次バッチが確認済みにした記事でも取り直すために付ける。`--dry-run` は、この段階で用語DBのW列（GAP確認日）を書かないために付ける。

```bash
cd ~/workspace/article-creator
python3 scripts/collect_edit_gaps.py --term {用語} --recheck --dry-run --out-dir logs/gaps/retro-$(date +%F)
```

出力された `logs/gaps/retro-{日付}/{用語}.md` を読む。初稿（`drafts/_baseline/`）、公開版URL、生成バージョン、手が入った箇所の一覧が入っている。

「差分を取る対象は無し」と出たとき（用語DBのステータスがまだ「公開」に変わっていない等）は、`drafts/_baseline/{用語}_{生成バージョン}.md`（初稿）と `drafts/{用語}.md`（レビュー済みの最終版）を直接突き合わせる。この場合は、WP上で公開後に直した箇所が比較に入らないことを、Step 3の冒頭で1行伝える。

### 2-2. セッションのやりとり

同じ会話（またはyuyaが指定したセッション）を読み返し、次を拾う。

- yuyaが「分からない」「直感的でない」「区別がつかない」と指摘した箇所と、その理由
- 作っては捨てた案（たとえ・言い回し・構成）と、捨てた理由
- 改稿の途中で事実や意味がずれ、レビューで戻した箇所
- やりとりの中で出た、次の版（プロンプト・Critic・工程）への改善案

推測で補わない。会話に無いことは書かない。

## Step 3: 仮説をyuyaにぶつける

### 3-1. 直した理由・何がいけなかったかの仮説

差分（2-1）とやりとり（2-2）の両方から、項目ごとに次の4点を1〜2行で書く。

- 何がいけなかったか（初稿と公開版の要点、またはやりとりで起きたことを短く引く）
- なぜそうなったと考えるか（仮説）
- 当たる原則：`prompts/02_polishing.md` の P1〜P7、`CLAUDE.md` の F1〜F6 のどれか。どれにも当たらないときだけ (B) と書く
- 確度（高・中・低）

次の差分は数えずに「数えない差分」として1行にまとめる。関連用語の付け替え、URLだけの追記、画像の差し込み、表記ゆれの吸収漏れのように、執筆の指示を変えても防げないもの。

仮説は推測として書く。yuyaの意図を断定しない。似た理由の箇所はまとめ、差分由来・やりとり由来を合わせて多くても7項目に絞る。

### 3-2. 修正レベルの仮説（1〜3）

数字が大きいほど手が入ったことを表す。差分の量ではなく、3-1で立てた理由から決める。

- **1（軽い）**：語の置き換えや言い回しの手直しにとどまる。記事の骨格・事実・論点は初稿のまま使えた
- **2（中くらい）**：文や段落の単位で書き直した、または段落を削った箇所がある。ただし骨格と事実は初稿のまま使えた
- **3（重い）**：事実の誤りを直した、構成を組み替えた、または読み手に伝わらない説明を作り直した

レベルと、そのレベルにした理由を1行で添える。

### 3-3. 出し方

チャットに次の順で出す。見出しは付けず、短くまとめる。

1. 記事名・ID・カテゴリ・生成バージョン・公開版URL（2-1で直接突き合わせた場合はその旨）
2. 修正レベルの仮説と理由1行（共同編集者の評価が付いていれば並べる）
3. 何がいけなかったかの仮説（番号つき、多くて7項目。やりとり由来の項目はそうと分かるように書く）
4. 数えない差分（1行）
5. 最後に1行で「違うところを教えてください。合っていれば『OK』で確定します」と聞く

yuyaの確定前には、Doc・観測ログ・用語DBのどこにも書き込まない（Step 1.5 の公開状態の反映は除く）。

## Step 4: 是正を受けて確定する

yuyaの是正を反映し、確定版を1回だけ短く見せる。yuyaが「OK」と返したら（または「記載して」と指示したら）、Step 5へ進む。是正の内容は、仮説とどこが違ったかが分かる形で残す（仮説の精度を後で見直すため）。

## Step 5: 確定内容を書き込む

### 5-1. 記事のGoogleドキュメント

- **タイトルの頭**に `（{レベル}）` を付ける。既存の接頭辞（`【WP移行済み】` など）より前に置く。例：`（3）【WP移行済み】エージェンティックRAG`。リネームは Google Drive の update_file で行う（リンクは変わらない）。すでに数字が付いている場合は上書きせず、yuyaにどちらを残すか聞く
- **本文の一番下**に、見出し2の節 `修正ふりかえり（レベル{n}）` を足し、次の順で書く。本文の先頭には何も足さない
  1. 1行目：`修正レベル：{n}（{軽い/中くらい/重い}）。{レベルの理由を1文}（{YYYY-MM-DD} yuya確認）`
  2. 見出し3 `何がいけなかったか`：番号つきリストで、差分由来とやりとり由来の項目を書く。各項目は「何がいけなかったか → 読者にどう影響したか → 何が必要だったか」の順で2〜3文
  3. 見出し3 `直す途中で起きたこと`：改稿の途中で事実の意味がずれ、レビューで戻した箇所があれば書く。無ければこの見出しごと省く
  4. 見出し3 `次の版で試したいこと（候補）`：やりとりで出た改善案を箇条書きで。案は「候補」として書き、決定事項として書かない
- 文体は記事と同じく、体言止め・受動態を避け、主語を明示する
- 書き込みは Google Docs の update_doc で、リード済みの revisionId を付けて1回のバッチで行い、書いたあとに読み返して見出しと番号の付き方を確かめる

### 5-2. 観測ログ

`prompts/learned/observations.md` の末尾に、今日の日付の節を足し、次の形で書く。週次バッチと同じ形に揃え、改訂案の材料として使えるようにする。やりとり由来の項目も同じ節に入れる。

```markdown
## {YYYY-MM-DD}

### {用語}（{G-ID} / {生成バージョン}） — 未反映（yuya確認済み）
- カテゴリ: {カテゴリ名}（ID: {category_id}） / 修正レベル: {n}
- **(A) {分類} / {P番号}**: {確定した理由}
- **(B) {分類}**: {確定した理由}
- 仮説との違い: {yuyaが是正した点。なければ「なし」}
```

同じ用語・同じ版の自動分類の節（`— 未反映`）がすでにあれば、二重に数えないよう、その節の見出しを `— 未反映（yuya確認版に統合）` に書き換える。

### 5-3. 用語DBのGAP確認日

週次バッチが同じ記事をもう一度拾わないよう、ローカルで次を実行してW列に確認日を書く。用語DBのステータスがまだ「公開」でなく、2-1で対象が見つからなかった場合は、ステータスが変わってから実行する（完了報告でその旨を伝える）。

```bash
cd ~/workspace/article-creator
python3 scripts/collect_edit_gaps.py --term {用語} --recheck --out-dir logs/gaps/retro-$(date +%F)
```

### 5-4. やらないこと

- `prompts/` は書き換えない。改訂案づくりは週次バッチ（未反映が3本たまったら proposal を出す）に任せる。観測ログへの追記は 5-2 のとおり行う
- gitのコミット・pushはしない。必要ならyuyaに1行で伝える
- Slackには投稿しない

## 完了報告

2〜3文で返す。確定したレベル、書き込んだ先（用語DBのステータスと公開URL・Docのタイトルの頭・Docの末尾のふりかえり・観測ログ・W列）、観測ログの未反映が何本たまったかを伝える。3本以上たまっていれば、週次バッチで改訂案が出ることを添える。W列を後回しにした場合は、その理由を1行で添える。
