# データの出どころと、Redash 依存を外す方針

## いまのデータの流れ

```
Redash    ──> master シート        荷主のチャネル連携状況、規約合意日、請求開始日/終了日
BigQuery  ──> Target_data シート   対象月の出荷件数と段別の内訳
                    ↓
              create_csv シート    Admin へ投入する調整額CSV
                    ↓（人間が投入）
              bill_adjustments     Admin に登録された調整額（投入後の突合に使う）
```

`Target_data` の元は `openlogi-live` > `test_yuya` > `oms_bills_data`。

## 各シートが持つべき列

検証ツールはこの列名を前提にしている。列名を変えるときは
`scripts/verify_oms_adjustment.py` と `scripts/parse_oms_sheets.py` も一緒に直す。

### master

| 列 | 意味 | 検証での使われ方 |
| --- | --- | --- |
| `code` | 荷主コード | CSV の `acc` と突合する主キー |
| `nickname` | 荷主名 | レポート表示のみ |
| `連携先EC` | 連携チャネルをカンマ区切りで並べたもの | 課金対象判定 |
| `ショップ有効` | 上と同じ順・同じ個数の true/false | 課金対象判定（有効なものだけ数える） |
| `アカウント有効` | 1 / 0 | 無効アカウントへの請求を検出 |
| `規約合意日` | 合意書を受領した日 | 請求開始日の登録漏れ検出 |
| `請求開始日` | 請求を開始する月の1日 | 対象月に請求すべきかの判定 |
| `請求終了日` | 請求を終了する月の末日 | 同上 |

`連携先EC` と `ショップ有効` は順番で対応づけている。**この2つの並び順がずれると
課金対象の判定が丸ごと狂う。**クエリを直すときは、必ず同じ `ORDER BY` で並べること。

### Target_data

| 列 | 意味 |
| --- | --- |
| `acc` | 荷主コード |
| `wb` | 倉庫コード |
| `target_term` | 対象月 `YYYY-MM` |
| `target_date` | 対象日（対象月の末日） |
| `shipment_cnt` | 対象月の出荷件数（課金対象分のみ。モール出荷は含めない） |
| `-500` 〜 `20000-` | 段別に配分した件数 |
| `fixed_fee` | 基本利用料 |

### create_csv

Admin の調整額CSVテンプレートそのもの。1行目が【必須】の説明、2行目が列名、3行目以降がデータ。

`acc` / `warehouseBaseCode` / `targetDate` / `detailDiv` / `taxExemptAmount` /
`taxInputDiv` / `amount` / `memo` / `wholesaleDiv` / `wholesaleValue` / `staffMemo`

### bill_adjustments

`code` / `target_date` / `amount` / `memo`。Admin から取得した登録済みの調整額。

## Redash 依存を外す

`master` を Redash から BigQuery に寄せると、請求に使うデータの出どころが1つになる。
その方が、月次で見るべき場所が減り、片方だけ更新される事故もなくなる。

### 移行の考え方

いま Redash が返しているものを、そのまま BigQuery のビューにする。
新しいクエリを一から書くのではなく、**Redash の既存クエリの SQL をそのまま持っていくのが安全**。
Redash も BigQuery を見ているなら、SQL はほぼそのまま動く。別のデータソース（本番DBのレプリカなど）
を見ている場合は、テーブルの対応づけから確認が必要になる。

### 移行のときに満たすこと

1. **出力列を変えない。** 上の master の列定義をそのまま維持する。
   列名を変えたくなっても、移行と同時にはやらない。一度に2つ変えると、
   差分が出たときにどちらが原因か切り分けられなくなる。

2. **並行稼働で1〜2ヶ月ぶん突き合わせる。** 新しいビューと Redash の結果を同じ日に取り、
   全行が一致することを確認してから切り替える。差分が出たら、その荷主が
   請求対象かどうかに影響するかを必ず見る。

3. **`ショップ有効` の並び順を `連携先EC` と揃える。** 上で書いたとおり、ここがずれると判定が狂う。
   `STRING_AGG(... ORDER BY <同じキー>)` のように、両方に同じ並び順を明示する。

4. **切り替え後の初回は、前月の請求結果と突き合わせる。**
   `scripts/verify_oms_adjustment.py` に前月の CSV を `--prev-create-csv` で渡し、
   `mom.前月あり今月なし` が出ないことを確認する。データソースの切り替えで
   荷主が落ちていれば、ここで請求漏れとして止まる。

### 移行後の姿

```
BigQuery  ──> master シート        （マルチチャネル連携＋契約状態）
          ──> Target_data シート   （出荷件数）
```

GAS 側は「マルチチャネルデータを更新」の中身を Redash 取得から BigQuery 取得に差し替えるだけで、
カスタムメニューの構成も、このスキルの手順も変わらない。

## master に載らないもの（自動判定できない項目）

検証ツールが原理的に判定できないもの。**人間の確認が必要な理由がここにある。**

| 項目 | なぜ判定できないか | どう扱うか |
| --- | --- | --- |
| BASE の新アーキ／旧アーキ | master の `連携先EC` はどちらも `thebase` としか出ない。Admin の `(Fraise)` 表記でしか区別できない | `master.課金条件が判別不能` として WARN を出し、人間に回す |
| 規約合意書の実在 | master にあるのは日付だけ | 合意日の登録運用に依存する。登録漏れは `master.請求開始日未登録` で拾う |
| キャンペーン適用（6ヶ月無料） | master に適用フラグがない | 対象荷主を別途把握し、目視で除外を確認する |
| 出荷件数の正しさ | BigQuery が返した件数を正として扱っている | モール出荷の除外・キャンセル分の扱いは、クエリ側の責任 |
| OPL 複数アカウントでのシングルチャネル運用 | アカウントをまたぐ名寄せ情報が master にない | 課金対象外だが、アカウント単位では判定できない。営業側の運用に依存する |

これらを master に列として持てるようにすると、自動判定できる範囲が広がる。
特に **BASE の新旧アーキ判定を master に1列足す**のは効果が大きく、
WARN が1つ丸ごと消えて、判定の確からしさが上がる。
