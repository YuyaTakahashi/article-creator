# 情報収集プロンプト

指定されたトピックについて出典を読み込み、次の3つを作ってください。文章の書き方は次の工程（02_polishing.md の執筆原則 P1〜P7）で整えるので、ここでは**事実を集めて出典と対にすること**を最優先にします。

1. **出典台帳**：記事に使える事実を、出典の引用と1対1で並べたもの
2. **成立条件メモ**：用語が成り立つ条件と、隣の用語との境界
3. **初稿**：台帳の事実だけを使った、下の観点に沿う下書き

トピックに複数の意味合いがある場合は、次のコンテキストで意味合いを特定してください。

コンテキスト：
{context}

## 一次参照ソース（ディープリサーチで収集済み）

下記は NotebookLM Deep Research が事前に収集したソースの一覧である。各ソースを WebFetch で実際に読み込んでから使うこと。

{sources}

ソース一覧が空、または「ディープリサーチ未実施」と書かれている場合に限り、Web 検索で独自にソースを集めてよい。提示されたソースを先に読み、足りないときだけ追加の検索で補う。

## 出典の扱い（必ず守る）

- あなたの内部知識や推測で事実を書かない。**このセッションで実際に読んだページの文章**だけを出典にする。
- 1つの情報源に頼らず、できるだけ複数の信頼できる情報源で確かめる。
- 出典が読めなかった（403・CAPTCHA・要約しか見えない）ときは、その出典を使わない。読めなかったことを台帳の末尾に書く。
- 信頼できる事実が確認できない、または情報が矛盾している場合は、推測で埋めず「信頼できる情報源が見つかりませんでした」と書く。

## 検索言語と参照ソースの優先順位

1. **最優先**: 英語の一次情報・原典（提唱者本人の論文・書籍・公式ブログ、学術論文、Nielsen Norman Group / IDEO / IxDA / ACM / IEEE などの権威ある機関の文書）
2. **次点**: 英語の二次情報（信頼できるテックメディア、専門家による解説・レビュー論文）
3. **補助**: 日本語の解説記事。一次情報の代わりにはせず、日本語特有の文脈を補う目的でだけ使う

日本語ソースしか見つからない概念（日本独自のメソッドなど）は、その旨を台帳に書く。

# 出力1：出典台帳

記事に入りうる事実を、1行1事実で並べる。人名・年・所属・数値・実験の手順と結果・因果の主張・提唱者の動機・普及の理由は、どれも事実として扱う。

```
C01 | 事実（日本語1文） | 出典URL | 引用（出典の原文をそのまま。英語なら英語のまま、要約しない）
C02 | ...
```

- 引用は、その事実を直接言っている箇所を切り出す。引用から一段推論しないと言えない事実は、台帳に入れない。
- 仕組みの説明が仮説・モデルなら、事実の欄に「〜という説明（モデル）がある」と書く。モデルを事実として書かない。
- 読めなかった出典：URL と理由（403・CAPTCHA など）を末尾に並べる。
- **例の筋**：記事で例に使いうる作品・事件・実験・事例は、その筋（誰が・何をして・どうなったか）を直接言っている引用も台帳に入れる。読者がその例を知らなくても筋が追えるようにするためである。筋を言う引用が見つからない例は、事実の欄の頭に「（筋未確認）」と書き、記事の例には使わない。
- **応用例**：研究や原典の中の例とは別に、読者が自分の仕事に重ねられる実在の事例（製品・サービス・建築・組織の取り組みなど）を1つ以上集める。出典自身がその事例をこの用語、またはこの用語の型と結びつけていることを引用で示す。出典が結びつけていない事例は、事実の欄の頭に「（当てはめ・出典なし）」と書く。記事ではその事例を作例として扱う。
- **説明の材料**：その分野を初めて知る読者が、つまずかずに読めるようにするための材料を集める。とくにAI・ソフトウェアなど技術系の用語は、定義に出てくる語そのものを読者が知らないことが多いので、次の種類を探す。（手計算）だけは、数値で動く仕組みがある用語（確率・指標・計算式・繰り返しの掛け算など）に限って探し、そうでない用語では作らない。記事でどれを使うかは書き手が選ぶ材料であり、全部を使う前提ではない。
  - （前提）用語を理解するのに要る概念を、読者に近い順に2〜4段並べる（例: AIは大量の例から学ぶ → その仕組みの一つがニューラルネットワーク → 学習とは予測のずれをもとに中身を少しずつ直すこと）。各段は日常語の1文にし、入門書・公式ドキュメント・用語集など、その概念をやさしく説明している出典の引用を付ける。
  - （働き）定義に出てくる専門用語を、仕組みではなく「何をするためのものか」で言い換えた1文（例: 勾配＝各層をどれだけ直すかを示す値）。言い換えを直接言っている引用を付ける。
  - （手計算）※数値で動く仕組みがある用語だけ。仕組みを、小さな数で読者が自分で確かめられる計算にしたもの（例: 0.5を3回掛けると0.125になる）。計算そのものは事実ではなく説明なので出典欄は「—（計算）」とし、どの台帳IDの仕組みを示す計算かを事実の欄に書く。計算の正しさは書いた時点で確かめる。
  - （たとえ）身近な物や場面に置き換えた説明。出典がそのたとえを使っていれば引用を付ける。出典の無いたとえは事実の欄の頭に「（たとえ・出典なし）」と書き、どこまでが実際の仕組みと合い、どこからずれるかを1文で添える。ずれが読者の誤解につながるたとえは入れない。
  - （結果）用語が起きたとき・使ったときに、読者から見て何が起きるかを、読者の言葉で言った1文（例: 学習が進まない／学習が不安定になる）。引用を付ける。

# 出力2：成立条件メモ

```
用語の種類: 道具・手法・概念 ／ 現象・効果・バイアス ／ 指標・計算 のどれか
成り立つ条件:
  - 条件1（台帳ID）
  - 条件2（台帳ID）
隣の用語との境界:
  - {隣の用語}: どの条件が違うとそちらになるか（台帳ID）
出典が確かめた範囲: どの場面・感覚・反応で確かめられているか（例: 音でも光でも起きた／反応はキー押しでのみ確かめた）
通し例の候補: 記事全体で使い回す具体例を1つ。成り立つ条件を1つずつ挙げ、この例がそれを満たす理由を書く
応用例の候補: 読者の仕事に近い事例を1つ（台帳ID）。用語の条件を満たす理由と、出典が結びつけているか（当てはめか）を書く
```

- 現象・効果・バイアスの用語では、隣の用語との境界を必ず調べる（例: サイモン効果と刺激反応適合性は「位置が答えの手がかりになっているか」で分かれる）。
- 通し例は、条件を1つでも満たさなければ別の例に替える。

# 出力3：初稿

台帳にある事実だけを使い、次の観点で下書きする。観点は「調べる観点」であり、台帳に裏づけが無い観点は空欄のまま飛ばす（推測で埋めない）。各段落の末尾に、使った台帳IDを `[C01,C03]` のように付ける。

## 0. 最小限の説明
用語を20〜35文字で定義する（定義の型は 02_polishing.md の P2）。分野から入り（例:「AIの学習で、」）、用語に含まれる専門語（勾配・誤差など）を使わず、台帳の（働き）（結果）の言葉で言い切る。

## 1. 導入と定義
用語の定義と、通し例。既存の概念の改良・発展形なら、ベースの概念と何が変わったか。定義文に読者の知らない語が残るときは、台帳の（前提）を1〜2文、定義文の前に置いてよい。

## 2. 生まれた背景（語源・提唱者）
誰がいつ何を示したか。台帳にあれば、当時の困りごと・狙い・その結果何が変わったか・広まった理由。提唱の根拠になった実験があれば、その内容（何を・どう調べ・何が分かったか）。

## 3. 効果・現れ方
道具・手法・概念なら、使わない場合と使う場合の違い。現象・効果・バイアスなら、どれくらいの大きさで、どんな形で現れるか。台帳にある数値・条件による変化・反証を含める。

## 4. 仕組み
台帳にある範囲で、何が・何に影響して・何が起きるか。記事では定義セクションに含めるので、独立した章にしない。

## 5. 実務でどう使われるか
台帳にある範囲で、どの工程で使うか・何が成果物として残るか・誰と使うか・失敗しやすい点。研究で効果を測っていない当てはめは、作例であることを書く。成立条件メモの「応用例の候補」を必ず1つ使い、読者が自分の仕事でどう重ねるかが分かる場面として書く。

## 関連用語
隣の用語（成立条件メモの境界に出たもの）を含めて、合わせて知っておくべき用語を並べる。

# トーン
「である」調。箇条書きを避けて文章で書く。分野固有の専門用語は、知らない読者を想定して実際に起きていることに言い換える。言い換えには台帳の（働き）を使い、仕組みは（手計算）か（たとえ）で見せ、起きることは（結果）の言葉で言う。
