# 執筆ルール改訂案（2026-09-07）

対象: 未反映の観測 3本ぶん（CAGR・IaC・ループエンジニアリング）

前提として、IaC は v1、ループエンジニアリングは v3、CAGR は v2 の稿である。v10〜v15 で入れた指示（リード文4段落構成・語源の①省略例外・証拠の最小化）は、いずれの稿にも効いていない。したがって以下は「v15 でも塞げていない」ことの証明ではなく、**v15 の条項と重ならない範囲で残っている型**に絞って挙げる。

---

## 1. 語源・提唱者に出す人名・製品名の数に上限を置く

- **根拠**: IaC・ループエンジニアリングの2記事で、どちらも語源セクションが最大の削減対象になった。IaC は Martin Fowler / Mark Burgess・CFEngine / Luke Kanies・Puppet / Adam Jacob・Chef / Patrick Debois・devopsdays / HashiCorp・Terraform / Kief Morris の7組を並べたが、公開版は Kief Morris と書籍『Infrastructure as Code』の1点だけを残して2文になった。ループエンジニアリングも swyx の講演・LangChain の4層整理・IBM「Bob」・Osmani の定義の逐語引用が落ち、Peter Steinberger と Addy Osmani の1文だけが残った。
- **いまの記述**: `prompts/02_polishing.md` 149行目。「提唱当時の具体的なエピソード（実際のプロジェクト・製品・失敗事例）が入力テキストにあれば必ず残す。読者が背景を掴む手がかりとしていちばん効くので、要点を落とさない（①を省略する場合も、エピソード自体は②③の中で使ってよい）。**ただし要点を残すことと、量を増やすことは別である。エピソードは1〜2文の要点提示にとどめ、当事者の発言の再現・周辺人物の反応・場面描写までは書き込まない。**」— v15 のこの条項は1つのエピソードの書き込み量を抑えるものであり、**エピソードを何個並べてよいかには触れていない**。系譜を並べる書き方はこの網をすり抜ける。
- **改訂案**: 149行目の直後に次の1項を足す。

  > **語源・提唱者に出す人名・企業名・製品名は、合わせて3組までにする。** 用語の呼び名が誰か一人に帰属しない場合（現場が自然に使い始めた語など）でも、前身技術の系譜を年代順に並べない。名前を出す枠は「その用語を最初に名づけた／広く定着させた人」「その考え方を1冊・1本にまとめた文献」「実装として最初に広まった製品」の3つに割り当て、埋まらない枠は空けたまま出さない。枠から漏れた名前は、固有名詞を使わず「構成管理ツールが1990年代から育っていた」のように性質だけで述べるか、書かない。

- **効かせ方**: いまの指示は「エピソードを残せ」と「量を増やすな」の両方を言うだけなので、書き手は"1つ1つは短いから大丈夫"と判断して個数を増やす。3組という数と、枠の割り当てを先に決めておけば、何を捨てるかが書く前に決まる。

## 2. セクション冒頭の「1文だけの結論段落」を、置く条件つきの指示に変える

- **根拠**: 冒頭の1文結論段落が人に削られる事象は、これで5記事目になる（G-011 効果セクション冒頭2文、G-074 マタイ効果の要約的トピック文、G-076 CAGR、G-013 IaC、G-077 ループエンジニアリング）。今回は1回で2箇所（ループエンジニアリングの語源「エンジニアリングという言葉が付くのは、輪の組み方そのものを設計の対象に据えるためである。」と効果「ループを設計すると、人間が手を動かす場所が『毎回の確認』から『合格基準づくり』へ移る。」）が削られ、IaC では結論文がリード文1文目の言い直しだったため**セクションごと**（H2「手順書でなく、コードで環境を作る」）落ちた。
- **いまの記述**: `prompts/02_polishing.md` 91行目「**各セクションの冒頭に、そのセクションの結論を1文だけの独立した段落として置く。** 詳細はその次の段落から書く。」と、104行目「**セクション冒頭の結論文は、直後の文の言い換えにしない。** 「〜が起きるのは〜だからである」と置いた1文が、次の文とほぼ同義になっていたら、結論文の側を削って一本化する。定義・リード文で述べた要点（例: 追加学習が要らない）を、後段セクションの入口でもう一度説明し直さない。」— 104行目は v3 で入れたが、削られた3文はいずれも直後の文の**逐語的な**言い換えではないため、この条件では止まらない。
- **改訂案**: 91行目を次に置き換える。

  > **セクション冒頭の1文結論段落は、必須ではなく「置いてよい」ものとして扱う。** 置いてよいのは、そのセクションが記事のどの主張ともまだ結びついていない新しい論点を立てるときだけである。次のいずれかに当たるなら置かず、本文の1文目から書き出す。
  > - 効果セクション：「使わない場合→使う場合」の前後対比そのものが結論を運ぶので、その手前に結論を置くと同じことを二度言うことになる
  > - 定義セクション：リード文①で定義を言い切っているので、その要点を別の言い方で立て直さない。**立て直した結果、そのセクションが「リード文の詳しい版」にしかなっていないなら、セクションごと作らずリード文に統合する**
  > - 語源・提唱者：①②③の順で語ること自体が構成なので、その前に総括を置かない

- **効かせ方**: いまの91行目は「置け」と義務化しているため、書き手は置き場所のないセクションにも結論文を作る。104行目の「言い換えにするな」という条件だけでは、言い換えでない結論文（＝それ自体は正しいが、そのセクションでは要らない文）を止められない。義務を条件つきの許可に変え、置いてはいけない3つのセクションを名指しすることで、判断が「書くかどうか」ではなく「どのセクションか」で決まる。

## 3. リード文の具体例は、定義段落に無い情報を足しているかで採否を決める（案）

- **根拠**: IaC とループエンジニアリングの2記事で、リード文の具体例段落が同じ位置から消えた。IaC は「たとえば、同じ設定のサーバーが10台必要なとき…」の3文がまるごと削除。ループエンジニアリングは「たとえば、コードを書くAIエージェントに『書く→テストを走らせる→失敗内容を読む→直す』という輪をひとつ持たせるとする。これでも動くが…」が、コードという舞台設定を落として一般的な説明に書き換えられた。どちらも例の前半2文が舞台設定に費やされ、締めの文が定義段落の主張の言い直しになっていた。
- **いまの記述**: `prompts/02_polishing.md` 93行目「**具体例（たとえば〜）は定義の直後に置く。** 語源や周辺の説明より先に出し、読者が像を結んでから細部へ進ませる。その例には、具体的な文書・場面・結果のいずれかを含め、読者が情景を思い浮かべられる粒度で書く。「たとえば」で始めながら中身が一般論のままの文（例：結論だけ書いて、何を検索し何が返るかを書かない）は書き直す。」— 求めているのは「例が具体的か」であって、**その例が定義に無い情報を足しているか**は問うていない。今回の2例はどちらも十分に具体的（10台のサーバー／コードとテスト）で、この条件では落ちない。
- **改訂案**: 93行目の末尾に次を足す。

  > **例は2文以内で書く。** 1文目で場面を置き、2文目でその場面がどうなるかを述べる。舞台設定に2文以上使っているなら、その例は重すぎる。**書いたあと、その2文が定義段落に無い情報を足しているかを確かめる。** 定義段落の主張を場面に置き換えただけなら、例を差し替えるか、例を置かずに定義から次の論点へ進む。

- **効かせ方**: 「具体的に書け」という指示だけだと、書き手は具体性を上げる方向にしか動かず、文数が増える。2文という上限を置けば舞台設定を削る圧力がかかり、「定義に無い情報か」を確認手順として書けば、言い直しの例が採用前に落ちる。ただし IaC の例は具体性という点では悪くない書き方だったので、人が削った理由が「重複」なのか「記事全体を短くする過程での巻き込み」なのかは差分からは確定できない。**この項目は案として出す。**

## 反映のしかた

1. 上の改訂案を prompts/ に反映する
2. `python3 scripts/recipe_version.py bump --note "{改訂の要約}"`
3. observations.md の該当記事を `— 反映済み(vN)` に書き換える
4. 旧版の記事は用語くんが作り直し候補として数える（`@用語くん 古い記事教えて`）

## 提案に入れなかったが記録した観測

- **効果セクションの「誰に効くのかを書き分ける」に従って書いた段落が、まるごと削られた**（ループエンジニアリング）。「効き方は立場によって違う。作り手のチームには…事業の側には…エンドユーザーに届くのは…」という段落で、指示文の言い回しをそのまま本文の書き出しに写している。実務セクションには「項目名をそのまま本文の語として使わない」という歯止めがあるが、効果セクション（158行目）には無い。観測1件のため今回は提案に入れないが、同じ型がもう1件出たら 158行目に同じ歯止めを足す候補になる
- 一度説明した語に後段でもう一度括弧注を付ける（IaC の「設定ドリフト」）、読者が知らない前提の企業名に初出で業種を添える（ループエンジニアリングの LangChain）、専門語を和語の比喩に訳したまま見出しに使う（IaC の「使い捨て」）。いずれも1件ずつなので、次回以降の観測で追う
